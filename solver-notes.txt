HeapGo solver notes
===================

Status
------
Done:   move table, negamax + transposition table in cmd_solve, time limit.
        Public tests: 80/80 marked pass, apart from genmove tests that
        depend on a random move.
To do:  (1) genmove should reuse the solver
        (2) alpha-beta pruning (last planned improvement)


1. What a position really is
----------------------------
Tokens are only ever taken from the top of a heap and never added back.
So the whole position is:
    - the current height of each heap, and
    - whose turn it is.
The tokens below each height never change.

The solver keeps a list of heights and plays/undoes moves on it directly.
It does NOT call HeapGo.play(), so solve never changes the game.
cmd_solve starts from len(heap) for each heap in self.game.heaps.


2. Move table (built once, when heapgo runs)
--------------------------------------------
Purpose: make playing a move fast. It does NOT choose the best move.

game.move_table[heap][height][color] = (new height, points gained)
Size is at most 20 heaps x 20 heights x 2 colors.

Worked example, one heap listed bottom to top:
[('b',3), ('w',5), ('b',2), ('b',4)]

    height | black moves      | white moves
    -------+------------------+--------------------
      4    | (1, 11)          | (3, 4)
      3    | (1, 7)           | (2, 2)
      2    | (1, 5)           | (0, 8)
      1    | (0, 3)           | (0, 3)
      0    | illegal          | illegal

"Play a move" = look up the entry, set that heap's height to the new
height, and set it back afterwards to undo. No token loop, no pop/push.


3. Negamax search (inside cmd_solve)
------------------------------------
- negamax(color) returns the best SCORE DIFFERENCE the player to move can
  still get: my future points minus the opponent's future points.
- For each non-empty heap: look up the move, apply it,
  value = gain - negamax(opponent), then undo it. Keep the max.
- No legal moves: return 0 (best starts at -inf, so this must be handled
  explicitly or -inf leaks into the parent).


4. Transposition table
----------------------
- Dictionary keyed by (tuple(heights), color), storing the negamax value.
  Starts empty each solve; only holds positions the search reaches.
- Many move orders reach the same position. Example: Black plays heaps 0
  and 2, White plays heaps 1 and 3, in any interleaving, gives the same
  heights. For k distinct heaps per side there are (k!)^2 times more paths
  than states, so this matters a lot. Alpha-beta alone does not remove it.
- Safe to cache because the value is the FUTURE score difference, which
  does not depend on points already scored.
- Lookup first; on a hit return immediately; on a miss search, store, return.


5. Turning the value into a solve answer
----------------------------------------
- Player p to move wins iff  margin + value > 0, where
      margin = score[p] - score[opponent]
  Scores come from game.score, and White's score starts at komi, so komi
  and any moves already played are both included.
  At the start of a game: Black to play wins iff value > komi,
  White to play wins iff value > -komi.
- Output: "b 0" style (winner + move) only if the player to move wins,
  otherwise just the winner. Game already over: just game.winner().
- The winning move comes from a loop over the root moves in cmd_solve
  (negamax returns only a value, not a move).


6. Time limit
-------------
- start = time.time() at the beginning of solve; negamax checks
  time.time() - start > self.timelimit on each cache miss and raises
  TimeoutError.
- cmd_solve catches it, prints nothing to stdout (message goes to stderr)
  and returns False, giving "= -1". Never guess the result.


7. Next steps
-------------
a) genmove: move the search into a helper returning (winner, move) or None
   on timeout. cmd_solve and cmd_genmove both call it. genmove plays the
   winning move if found, otherwise a random legal move.
b) Alpha-beta pruning. Caution: after a cutoff the returned value is only
   a bound, not exact. Caching it as exact gives wrong answers, so the
   table must store a flag (exact / lower bound / upper bound). Since solve
   only needs win vs loss, search with a narrow window around -margin.
c) Move ordering (larger gains first) to make alpha-beta prune more.
d) Boolean negamax was considered and rejected: the key would need the
   current margin too, which destroys transposition hits.
